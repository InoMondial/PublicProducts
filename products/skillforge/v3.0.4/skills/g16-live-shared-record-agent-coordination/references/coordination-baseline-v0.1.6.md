# G16-Live Shared Record Agent Coordination v0.1.6 — Canonical Candidate

## Status
CANONICAL NAMESPACE CANDIDATE after REFERENCE_SCOPE Stage 29 atomic namespace migration. Stage29 deterministic self-tests are PASS; final production certification remains gated by independent G12/G13.

## Purpose
Coordinate 2..N agents across different environments/accounts/surfaces without creating a scheduled chat or a new conversation. The user activates the participating agents once. A single manager agent retains coordination authority, delegates work, may execute work itself, and returns the final/user-facing coordination result.

## Activation
Use only when:
- two or more agents/surfaces must collaborate on one governed task;
- at least one participant can read/write the configured canonical shared record;
- the user has activated any surfaces that cannot be programmatically awakened.

Do not activate for a single-agent task that can be completed locally.

## Core topology
- STAR topology.
- Exactly one `coordination_manager` owns the global plan, user interaction and stop/continue decision.
- Workers report to the manager; workers do not independently re-plan the whole mission.
- The manager may assign independent work units to multiple workers in parallel.
- Parallel work is allowed only when the manager declares disjoint `resource_scope` and `parallel_safe=true`.
- Each work unit has exactly one active `action_owner`; no two agents may execute the same work unit concurrently.

## Shared record
Use one logical canonical append-only record for the active project/session.
- Preferred serialization: JSONL, one immutable event per line.
- Provider-neutral through a SharedRecord adapter; SharePoint is only one provider.
- Every write is read-latest -> concurrency/version check -> append one event -> write/append -> read-back verify.
- If the provider exposes atomic append or CAS/ETag/If-Match, use it.
- If the provider cannot provide atomic append/CAS, true concurrent writers are NOT safe. Degrade to sequential write ownership or block parallel record writes and state the limitation.
- The shared record is not a wake-up channel unless the provider actually supplies push/event delivery.

## Live wait
Default maximum live wait: 30 minutes.
Priority order:
1. native event wait / stream / webhook / thread event;
2. long-poll or provider task subscription;
3. delta polling using last_seen_event_id + version/ETag + byte offset/range;
4. full-record polling only when the provider offers no delta/range support, with that limitation stated explicitly.

Never summarize/reload the full growing record on every poll.

## Human interaction
The manager may keep workers LISTENING/WAITING while it asks the user for input. The manager records the user question and the resume condition. After user input, the manager appends the decision and resumes eligible workers. No worker bypasses WAITING_FOR_USER.

## Execution-surface recommendation — HARD GATE
Contract: `INC_G16_EXECUTION_SURFACE_RECOMMENDATION_V1` in `references/execution-surface-recommendation-contract-v1.yaml`.

Every execution-ready Handoff or cross-surface work order MUST carry an execution-surface suitability recommendation **next to** the model/reasoning recommendation. These are separate decisions:
- execution surface = where the work can run safely;
- execution profile = which model/reasoning floor is recommended on that surface.

Evaluate these standard execution options whenever they are relevant and currently available:
- `CODEX_WINDOWS_LOCAL`;
- `WORK_CLOUD`;
- `CHAT_BUSINESS_PRO` — ordinary Chat using the limited Business Standard Pro-profile allowance;
- `CHAT_STANDARD`.

For each option classify `REQUIRED | PREFERRED | ELIGIBLE | CONDITIONAL | NOT_ELIGIBLE`, based on the exact work unit's capabilities. Do not recommend a surface merely because it exists. In particular:
- local Windows PowerShell, local repository command execution, or local install/update smoke testing can require Windows Codex;
- long-running multi-system connected-app work without a local-shell requirement normally prefers Work Cloud;
- Business Standard Pro Chat is scarce and should be used for materially valuable bounded high-reasoning/independent review, not routine batch work;
- normal Chat may execute bounded review/connector-safe atomic units but is not the default surface for a long autonomous release mission.

The owner/operator remains the activation authority. G16 MUST NOT silently switch surfaces, open a limited Pro Chat, consume a scarce allowance, or claim a capability that was not verified. If more than one surface is eligible, list all eligible alternatives and identify one preferred surface only when evidence supports it.

Before declaring a work order execution-ready, derive hard system/environment requirements. If an exact requirement such as local Windows PowerShell, local Windows filesystem/application state, WSL/local shell state, a local browser profile/certificate, COM/desktop-only automation or local install smoke cannot be satisfied by an equivalent governed remote runner, the compatible surface is a **mandatory execution surface**. An incompatible surface MUST be marked blocked for that unit. Do not tell the user to try it anyway.

When a mandatory surface exists, the human-facing notice must make it unmistakable. For Persian output, G18 renders Persian first, for example: `سطح اجرای الزامی: 🖥️⚠️ Codex Windows — دلیل: PowerShell محلی ویندوز لازم است.` The icon is informative; the Persian lexical-start rule still applies.

## Minimum execution-profile recommendation — HARD GATE
Contract: `INC_G16_EXECUTION_PROFILE_RECOMMENDATION_V1` in `references/execution-profile-recommendation-contract.yaml`.

Every execution-ready manager-to-worker, Chat-to-Work, Chat-to-Codex, Work-to-Codex, agent-to-agent or cross-environment instruction MUST compute and carry the minimum sufficient ChatGPT execution profile before the task body is finalized. This is a recommendation/floor only, not permission for G16, an agent, Work, Codex or any generated instruction to change the active model or reasoning effort.

**Selection authority is always the human owner/operator.** G16 MUST NEVER automatically switch, select, click, invoke, configure, route or re-route the active model or reasoning-effort setting, even when the host exposes a programmatic or UI mechanism that could do so. G16 may only calculate, display and persist the recommendation. If a different profile is recommended, the user/operator decides whether to select it.

The computation MUST:
- resolve the target surface's actually exposed model and reasoning-effort inventory using read-only evidence only; never invent availability and never temporarily change model/effort merely to test availability;
- score task complexity, ambiguity/novelty, required reasoning depth, blast radius, tool orchestration, context/dependency load, verification burden, consequence/irreversibility, long-horizon recovery and surface brittleness;
- apply hard floors for production cutover, destructive/high-consequence operations, security/identity/key work, independent release certification and repeated lower-tier failure;
- recommend the lowest model + reasoning combination expected to satisfy correctness/evidence requirements with margin;
- persist the complete 0..4 factor vector used to compute the score so the recommendation is independently reproducible;
- state why a lower profile is materially risky and why a higher profile is unlikely to add material value;
- preserve G9's lowest-sufficient-resource principle and always treat the result as `USER_ADVISORY_ONLY`; G16 itself never enforces the model/effort change.

Required work-order block:

```yaml

  contract: INC_G16_EXECUTION_PROFILE_RECOMMENDATION_V1

  model: <exact host-exposed model name>
  reasoning_effort: <exact host-exposed effort label>
  minimum_floor: true
  selection_authority: USER
  factor_levels_0_4:
    semantic_complexity: <0..4>
    ambiguity_novelty: <0..4>
    reasoning_depth: <0..4>
    change_blast_radius: <0..4>
    tool_orchestration: <0..4>
    context_dependency_load: <0..4>
    verification_burden: <0..4>
    consequence_irreversibility: <0..4>
    long_horizon_recovery: <0..4>
    surface_brittleness: <0..4>
  score_0_100: <integer>
  complexity_class: <ROUTINE|STANDARD|COMPLEX|CRITICAL|FRONTIER>
  confidence: <LOW|MEDIUM|HIGH>
  why_not_lower: <bounded reason>
  why_not_higher: <bounded reason>
  escalation_triggers: [<bounded trigger>]
```

If the actual host profile is known and is below the computed floor, the instruction/result MUST surface `BELOW_RECOMMENDED_FLOOR_RISK`; for a critical floor G16 may block the governed critical action pending user selection, but MUST NOT change the model itself. If the user chooses a stronger profile, G16 should label it as above-floor and not imply material benefit unless a concrete escalation trigger exists.

The human-facing Chat/Work/Codex response that hands off an execution instruction MUST also display the recommended minimum model and reasoning effort in a compact visible form and, when a profile change is recommended, explicitly state that the user/operator must make that selection. Human rendering/localization is owned by G18; the exact model/effort names remain unchanged.

## Human dispatch notice and execution-surface terminology — HARD GATE
For human-facing cross-surface delegation, the standard umbrella term for `Chat`, `Work` and `Codex` is **execution surface**. An **agent** is an execution actor/worker that may operate on an execution surface; it is not a synonym for the surface itself.

Before or immediately after handing off an execution-ready instruction, G16 MUST provide the human owner a compact dispatch notice of no more than one or two short sentences stating:
- the target execution surface and, when relevant, the target agent/role;
- the action being delegated;
- the current state: about to execute, executing, completed, partial or blocked.

G18 owns localization/rendering of the notice. The notice is informational and MUST NOT duplicate the full work order, Handoff or evidence payload.

Standard human vocabulary:
- `execution surface` = Chat | Work | Codex | other explicitly verified host surface;
- `execution agent` = manager/worker/sub-agent/validator that performs work on a surface;
- use `cross-surface work order` for the instruction package sent from one surface/agent to another.

## Cross-surface execution method — HARD GATE
Contract: `INC_G16_CROSS_SURFACE_EXECUTION_DELIVERY_V1`.

Whenever G16 creates a prompt, command file, work order, Handoff, report, execution artifact or instruction for another Chat/Work/Codex/agent surface, G16 MUST apply the latest canonical G16 rules before generating the artifact. Missing G16 activation is `BLOCKED_G16_NOT_APPLIED`.

For administrative/infrastructure/Microsoft 365/Azure/supported web-service work, use a machine-first two-layer method.

**Layer A — represent the desired state as code/data whenever possible.** If the target state can be represented as a textual/declarative definition, script, package, template, source file, structured API payload or importable configuration, generate and validate that representation before any visual construction.

**Layer B — apply/activate it through the highest available machine route.** Evaluate this order:
1. PowerShell/native scripting;
2. official API/SDK;
3. official CLI or in-application command/import/deploy interface;
4. connected Plugin/structured tool;
5. structured browser automation;
6. visual UI/Computer Use.

Visual UI is a last-resort **fragment fallback**, not a workflow mode. If one exact fragment is proven impossible through higher routes, use UI only for that irreducible fragment, record its reason, then immediately return to the highest available machine route for all subsequent work. Expanding the surrounding workflow into UI merely because one fragment required UI is prohibited.

Examples:
- Power Automate: prefer generated/validated flow definition or package plus PowerShell/API/CLI/connector import/deploy/enable/read-back; use designer UI only for a proven UI-only parameter or interactive authorization fragment, then return to machine routes.
- Website UI: prefer source code/templates/styles/config plus Git/API/CLI deployment and automated tests; use visual UI only for irreducible visual inspection or a UI-only setting, then return to code/API/CLI.

On Windows Codex with direct terminal capability, PowerShell 7 (`pwsh`) is mandatory first candidate. Browser/UI before the PowerShell/API/CLI probe is prohibited. Work Cloud must never invent direct PowerShell capability; use connected/API/structured routes according to the verified surface capability. Lower-priority fallback requires an approved reason code from the contract.

All writes require read-before-write, least privilege, safe preview/WhatIf when applicable, post-write independent read-back and rollback awareness.

Machine-first/UI-last acceptance also requires: higher machine routes exhausted or proven inapplicable before UI; each UI fragment has a reason code; UI scope is minimized; and machine-route execution/read-back resumes immediately after the UI-only fragment when available. Credentials/MFA/secrets remain outside prompts/Handoffs/logs.

## Remote-reference-only delivery — HARD GATE
Generated files/prompts/Handoffs/reports/command files/execution artifacts intended for the user or another surface MUST first be persisted to the governed remote authority selected by G1/G17:
- GitHub for code/config/machine governance/versioned source and lightweight SharePoint pointer/provenance records;
- SharePoint for governed human/operational documents, Handoffs, reports and execution task files;
- document-class binaries such as DOC/DOCX/XLS/XLSX/XLSM/PDF/PPT/PPTX are SharePoint-only durable artifacts; a dual-publication requirement may create only a GitHub pointer/provenance record, never a duplicate document binary.

After remote write + read-back, transfer only the verified remote link or stable reference. Do not hand the local/sandbox file itself to the user or another surface; do not use direct file attachment or inline full-file content as a substitute for governed publication. Failure is `G16_REMOTE_REFERENCE_ONLY_DELIVERY_FAILED`.
